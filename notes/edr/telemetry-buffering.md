# 遥测缓冲：为何采集质量取决于队列和丢失记录（N11）

## 一句话
生产速率长期超过消费速率时，任何有限缓存都会填满；必须把丢失与覆盖范围作为调查证据的一部分。

## 原理
以下都是教学容量假设，不是产品实测。1000台主机、每台20条/秒、每条300字节：总量为6,000,000字节/秒，约518.4 GB/日，尚未计算索引、副本和协议开销。

| 条件 | 算式 | 结果 |
|---|---|---|
| 单机256 MiB磁盘缓存、20条/秒、完全断网 | 268435456 / (20×300) | 约12.4小时 |
| 同样缓存、1000条/秒 | 268435456 / 300000 | 约14.9分钟 |
| 4096条空队列，产1000条/秒、消800条/秒 | 4096 / (1000-800) | 约20.5秒填满 |

回调里不宜直接联网。一个教学固定队列的生产端如下；ring、锁、head/tail/used均需要预先初始化，数组位于适合执行级别的非分页内存。此为未编译的驱动接口片段。

```c
BOOLEAN TryPushCopy(const EVENT *e) {
    KIRQL old;
    BOOLEAN ok = FALSE;
    KeAcquireSpinLock(&queueLock, &old);
    if (used == CAPACITY) {
        ++lost;
    } else {
        ring[tail] = *e;
        tail = (tail + 1) % CAPACITY;
        ++used;
        ok = TRUE;
    }
    KeReleaseSpinLock(&queueLock, old);
    return ok;
}
```

消费者在同一锁下取出并更新head/used，在锁外序列化和落盘。事件内不能留下已失效的指针；锁下复制应有上限。代码只示范多生产者受锁队列，不声称实现高性能无锁环。

### 从队列到可靠传输
给事件分配 `host/boot/sequence` → 本地写入待确认批次 → 压缩发送 → 服务端确认 → 删除已确认批次。确认丢失导致重发时，服务端按事件键去重。重发可减少网络中断引起的丢失，不能恢复入队之前已经丢掉的记录。

假设序号100、101、102中101入队失败，中心看到100和102，可保留缺口；还应上报丢失计数与时间区间，避免把“缺失某条行为”当作没有发生。ETW自身也有EventsLost等会话统计，[官方结构说明](https://learn.microsoft.com/en-us/windows/win32/api/evntrace/ns-evntrace-event_trace_properties)。

## 审计
量测平均与峰值事件速率、记录尺寸分布、队列占用、丢失数、磁盘限额、重发重复和查询延迟。冷热分层与事件过滤要公开保留窗口；筛除的数据会降低未来调查能力。

## 易错
- 缓存只有延迟作用，不会解决长期吞吐量不足。
- 本地写入、服务端接收、索引可查询是三个完成阶段。
- 有序序号用于识别传输/采集缺口，不自动把多CPU的所有行为变成严格因果顺序。
- 本页预算是算术示例，未做实际驱动压力测试。
